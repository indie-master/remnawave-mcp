# Модульный кандидат: администрирование и кабинет

Это расширение существующего проекта, не обещание полной автоматизации всех операций Remnawave. Рабочие проверки и первоначальный MCP сохранены. Ниже описаны реальные границы модулей. Серверная приёмка, проверка ресурсов, домена и прав токенов обязательны перед публичным использованием.

## Режимы

| Модуль | По умолчанию | Реализовано |
| --- | --- | --- |
| Прежние проверки | Без изменения принятого режима | 14 отчётов, локальная грамматика, кеш команд, свежие данные |
| Inline-меню | Автоматически при расширенном интерфейсе | Начальное сообщение, редактирование, «Свернуть / Открыть меню», без нижней клавиатуры |
| Голос администратора | Выключен | Локальный CPU/int8 ASR, Ogg, 30 секунд по умолчанию, максимум 60; известные команды и кеш без ИИ, новые только после подтверждения |
| Пользовательские карточки | Выключены | Точный username/числовой ID, статус, срок, трафик; ссылка только после подтверждения |
| Изменения пользователей | Выключены | Разрешённые поля, продление, включение/отключение; предпросмотр и одноразовое подтверждение |
| Административный MCP | Отдельный запуск | Обезличенная сводка и создание заявки; нет инструмента исполнения/подтверждения |
| Кабинет | Выключен | Почта + пароль, аккаунт, собственный статус подписки и баланс; первоначальную привязку выдаёт администратор |
| Оплата | Выключена | Ручные RUB/USDT, проверенный ID поступления, одноразовое зачисление |
| Продление из баланса | Цена 0 блокирует покупку | Предпросмотр, подтверждение администратора, резерв/списание, защита от неопределённого результата |
| Поддержка в кабинете | Локальные FAQ/человек | Изолированная история, приватный кеш, общая только проверенная база знаний |
| Подписочный ИИ поддержки | Выключен | Минимальный текстовый контекст, без инструментов; общий ограничитель с административным ИИ |
| Интернет-поиск | Выключен, лимит 0 | Opt-in Brave API, только запрос инструкции для заданного приложения, разрешённые домены, кеш публичных ссылок |
| Скриншоты/видео поддержки | Выключены | Локальный OCR PNG/JPEG и до 3 кадров MP4 ≤30 секунд; неподходящее игнорируется, текст проверяет администратор |

Все операции панели не превращены в универсальный write-шлюз. Bulk-действия, удаление, изменение конфигураций/нод и произвольные HTTP/shell не добавлены. Клиентская поддержка сейчас находится в кабинете; текущий административный Telegram-бот не открыт всем клиентам и не заменён вторым получателем. Автоматических рассылок нет.

## Конфигурация без кода

### Управление пользователями и ручная сверка

В расширенном меню «Статистика и пользователи» объединяет общую сводку, онлайн, пользователей, ресурсы, процессы, трафик и версию. В сводке пользователей показаны только состояния аккаунтов. «Ноды» открывает сводку по состояниям, из неё можно перейти к списку и карточкам нод. Кнопки «Назад» ведут к родительскому экрану. Переходы по кнопкам редактируют текущее сообщение бота.

При `ADMIN_USER_READ_ENABLED=true` раздел «Статистика и пользователи» → «Пользователи» открывает поиск по точному ID/username, части имени и Telegram ID. Списки содержат по восемь пользователей. Доступны фильтры состояния и сортировка по ID, имени или сроку подписки. После карточки сохраняются страница, поиск, фильтр и сортировка. Точный поиск Telegram ID использует `users:stream`, так как фильтр Telegram ID в обычном списке 3.4.5 выполняет поиск по части числа. Показываются первые восемь точных совпадений с явной отметкой, если их больше. Для базового меню остаётся кнопка прямого поиска. Административные экраны сбрасывают контекст отчётов. Явные команды отчётов остаются доступны.

Карточка показывает состояние, срок, остаток времени, трафик, стратегию сброса, количество зарегистрированных устройств и лимит, последнюю активность, достоверный Telegram ID, описание и метку. При недоступном списке устройств показано «нет данных». Из карточки доступны подписка, трафик, устройства, соединения и разрешённые изменения.

После подтверждения выдачи ссылки появляются отдельные кнопки открытия и копирования. Ссылка длиной до 256 символов использует нативный `CopyTextButton`. Более длинную ссылку можно скопировать после открытия в браузере. Ограничение взято из [Telegram Bot API](https://core.telegram.org/bots/api#copytextbutton).

Продление доступно настроенными днями (`ADMIN_RENEWAL_DAYS`), календарными месяцами (1, 2, 3, 6, 9, 12), выбором дня в календаре или ручным вводом. Месяцы считаются по Москве от более позднего из текущего времени и срока подписки, с ограничением последним днём месяца. Календарь задаёт окончание в 23:59 МСК. Ручной формат — `ДД.ММ.ГГГГ ЧЧ:ММ` по Москве или ISO 8601 с часовым поясом. Ввод действует две минуты, одноразовое подтверждение — три минуты. «Операции» показывает 20 последних заявок без содержимого и ссылок. При `executing` или `uncertain` сначала сверяйте карточку и журнал. Клиент проверяет, что ответ PATCH действительно содержит заданные значения.

Трафик во всех новых экранах форматируется общим форматтером. Лимит задаётся кнопками 16/100/300/500/1000 ГБ, значением «без лимита» или вводом в ГБ до трёх десятичных знаков. Используется 1 ГБ = 1024³ байт. Ноль означает отсутствие лимита. Прежняя текстовая команда `trafficLimitBytes` по-прежнему принимает байты. Для стратегии добавьте `trafficLimitStrategy` в `ADMIN_ALLOWED_FIELDS`. Доступны реальные варианты 3.4.5 `NO_RESET`, `DAY`, `WEEK`, `MONTH`, `MONTH_ROLLING`.

Устройства открываются отдельными карточками. Для лимита есть кнопки 1/2/3/4/5/10 и ручной ввод. Текущие лимиты всегда берутся из панели. `ADMIN_DESTRUCTIVE_USER_ACTIONS=true` дополнительно открывает сброс текущего трафика и очистку всех устройств только для ID из `ADMIN_ACTION_USER_IDS`. Эти операции требуют прав `users:reset-traffic` и `hwid-user-devices:delete-all` на write-токене. При очистке перед записью сверяется весь список регистраций.

### Создание пользователей

Создание включается отдельными настройками. Заполните `ADMIN_CREATE_SQUADS` UUID разрешённых внутренних групп (до десяти), `ADMIN_CREATE_DEFAULT_GB` осознанно выбранным лимитом в ГБ, `ADMIN_CREATE_TRAFFIC_STRATEGY` и `ADMIN_CREATE_HWID_LIMIT`. Затем включите `ADMIN_CREATE_ENABLED=true` при уже разрешённом `ADMIN_WRITE_ENABLED=true`. Для чтения групп нужен `internal-squads:list`, для создания — `users:create`. Отсутствующие группы или неопределённый лимит блокируют включение.

Мастер предлагает username, дни, трафик, стратегию, лимит устройств, группы и необязательный Telegram ID. Кнопка теста на три дня берёт только явно настроенные defaults, включая четыре устройства по умолчанию для новых аккаунтов. Имя обязательно в обоих сценариях. Перед созданием проверяются уникальность имени, актуальные группы и контракт. Подтверждение одноразовое. При неясном результате новый POST для того же имени блокируется, даже если подготовлено второе подтверждение. После ответа панели доступна карточка созданного пользователя.

«Устройства» показывает зарегистрированные устройства и их количество. `hwidDeviceLimit` в `ADMIN_ALLOWED_FIELDS` разрешает изменение лимита через прежний write-доступ. «Соединения» запускает один короткоживущий запрос панели по пользователю. Получение результата происходит по отдельной кнопке. Отчёт показывает число адресов и время последнего наблюдения по нодам, без IP-адресов и сырых HWID. Именованные карточки нод доступны при включённых карточках и разрешённых отчётах `nodes,node_details`.

### Права для новых административных экранов

| Действие | Право токена Remnawave 3.4.5 | Локальная настройка |
| --- | --- | --- |
| Список и карточка пользователя | `users:list`, `users:by-id`, `users:by-username` | `ADMIN_USER_READ_ENABLED=true` |
| Устройства пользователя | `hwid-user-devices:list-by-user` | `ADMIN_USER_READ_ENABLED=true` |
| Запрос и проверка соединений | `connections:by-user`, `connections:by-user-result` | `ADMIN_USER_READ_ENABLED=true` |
| Именованный список и карточка ноды | `nodes:list`, `nodes:get` | `ADMIN_USER_READ_ENABLED=true`, разрешены отчёты `nodes,node_details` |
| Отзыв ключей / выпуск новой ссылки | `users:revoke-subscription` | `ADMIN_WRITE_ENABLED=true` и ID в `ADMIN_ACTION_USER_IDS` |
| Удаление одного устройства | `hwid-user-devices:delete` | `ADMIN_WRITE_ENABLED=true` и ID в `ADMIN_ACTION_USER_IDS` |
| Название и заметка ноды | `nodes:update` | `ADMIN_WRITE_ENABLED=true` и UUID в `ADMIN_ACTION_NODE_UUIDS` |

Оба списка целей по умолчанию равны `none`. `./botctl extensions` позволяет задать через запятую только конкретные ID или UUID, до 30 значений в каждом списке. После `./botctl check` и `./botctl apply` появятся соответствующие кнопки. Дополнительные права записи нужны только на отдельном write-токене. Разрешения проверяются при подготовке и повторно при подтверждении. Переход на новую версию сам не добавляет разрешения и не меняет существующие поля редактирования. Отзыв ключей может потребовать обновить профиль клиента. При полном отзыве панель также выпускает новую ссылку. Перезапуск и отключение нод, изменение адресов и сетевых профилей, массовые действия и удаление аккаунтов выполняются в панели. Сценарии используют [контракт версии 3.4.5](https://www.npmjs.com/package/@remnawave/backend-contract/v/3.4.5).

Ручная финансовая сверка отдельно выключена: `BILLING_RECONCILIATION_ENABLED=false` в `apps/business/.env`. Для её включения нужен и `BILLING_MANUAL_ENABLED=true`. `BILLING_REVIEW_DELAY_SECONDS=900`, допустимо 300..86400, задаёт минимальную задержку после резервирования; старые зависшие операции получают свежую задержку при первом открытии новой версией. Перезапуск её не сбрасывает. Пока есть pending/executing/uncertain-продление, новый запрос того же аккаунта блокируется.

В административном разделе оплат появляются «Ручная сверка» и журнал. Сначала администратор проверяет панель и журналы, убеждается, что старый запрос больше не выполняется, затем вводит `сверка ID выполнено основание` либо `сверка ID возврат основание` и отдельно нажимает «Сверено вручную». Это **только изменение учёта**, без повторной записи в панель. Возврат через бот требует административного модуля, блокируется при известном успешном подтверждении панели или активном запросе. Задержка сама по себе ничего не доказывает: скриншота клиента и предположений недостаточно. При сомнении резерв остаётся удержанным.

Состояние/ID исходной заявки повторно сверяются атомарно; возвращается ровно прежний резерв в исходной валюте, не произвольная сумма. Повторный callback, истёкший предпросмотр и конкурентное автоматическое завершение не возвращают деньги дважды. Журнал хранит основание, но не API-ключи и не сырой ID платёжной системы. Кабинет показывает только собственные заявки продления; глобальная сверка доступна лишь через закрытый Unix socket административного контура. Новые возможности не запускаются и не получают права автоматически при обновлении.

Для подписок поддерживаются варианты «подписка истекает / заканчивается», «подписки истекают / заканчиваются», «у кого подписка заканчивается» с поддерживаемым будущим окном. «Подписка истекает в ближайшие три дня» выполняет прежний отчёт на 3 дня без ИИ. «Через три дня» не заменяется незаметно на окно «в ближайшие три дня»: бот предлагает кнопки выбора периода, с расшифровкой и без запросов к модели или панели до выбора. При неразборчивом глаголе в короткой фразе «подписка … через три дня» бот также предлагает период, а не общее меню; произвольные слова не исправляются нечётким поиском и не превращаются в команды записи. Фильтры, точные даты, несколько разделов и неподдерживаемые периоды не угадываются.

Один дополнительный предлог «в» сразу после поддерживаемой команды чтения допускается локальной грамматикой: «пришли в статистику» — общая статистика, «пришли в статистику нод» — ноды. Это ограниченная обработка словесной формы, не исправление произвольного текста и не обещание идеальной точности ASR. Раздел определяется всей оставшейся фразой; дополнительные условия, отрицания, несколько разделов и повторные предлоги не отбрасываются. Модель распознавания, пороги уверенности и ресурсы контейнера не изменяются.

При неоднозначном голосовом запросе расшифровка также показывается администратору над кнопками уточнения — без вызова ИИ, запроса панели и записи текста в журнал. Запятые и повторные пробелы в обычных командах не мешают локальному разбору; отрицания, дополнительные фильтры и смешанные разделы по-прежнему не угадываются автоматически. Например, «Пришли, пожалуйста, статистику» — общая статистика, а «Пришли, пожалуйста, статистику нод» — ноды.

Распознавание аудио остаётся локальным и не расходует попытки модели. Известные голосовые команды выполняются локально или из кеша намерений со свежим чтением панели. Для незнакомой команды бот показывает распознанный текст только администратору и предлагает «Разобрать с ИИ / Отмена». До нажатия кнопки нет проверки готовности модели, резервирования квоты или передачи текста ИИ. Одноразовое подтверждение действует 3 минуты, исчезает после перезапуска и не повторяет запрос при ошибке. После подтверждения действуют прежние общие лимиты и защитные паузы; повторения успешных команд берутся из кеша. Текст и аудио в журналы или постоянное хранилище подтверждений не записываются. Обычные набранные текстовые команды не меняют своего поведения.

Из `apps/telegram-admin`:

```sh
./botctl extensions
./botctl business settings
./botctl check
./botctl apply-all
```

`extensions` редактирует приватную `.env.extensions`, образец — `extensions.env.example`. Старые `.env` и `.ops/settings.env` остаются совместимыми. `business settings` редактирует `apps/business/.env`, образец — `apps/business/.env.example`. Черновики проверяются офлайн, значения не исполняются как shell. Новые функции не включаются автоматически из-за обновления исходников.

Основные включатели: `VOICE_ENABLED`, `ADMIN_USER_READ_ENABLED`, `ADMIN_WRITE_ENABLED`, `BUSINESS_ENABLED`, `SUPPORT_AI_ENABLED`, `PORTAL_ENABLED`, `PORTAL_PANEL_READ_ENABLED`, `BILLING_MANUAL_ENABLED`, `MEDIA_ENABLED`, `SEARCH_ENABLED`. Для ИИ поддержки `SUPPORT_AI_ENABLED=true` нужен и в `.env.extensions` воркера, и в `.env` кабинета. Для управляемого из Telegram кабинета отдельно включить `BUSINESS_ENABLED=true`.

`ADMIN_ALLOWED_FIELDS` — ограниченный CSV `status,expireAt,description,email,telegramId,trafficLimitBytes,tag,hwidDeviceLimit,trafficLimitStrategy`. Это локальная политика разрешённых полей. Отдельный write-токен сохраняется командой `./botctl token write`. Нельзя включать write без карточек. Токен не передаётся модели.

Цены задаются в целых минимальных единицах: `PLAN_RUB_UNITS` — копейки, `PLAN_USDT_UNITS` — внутренние миллионные доли USDT, `PLAN_DAYS` — 1..366. Значение цены 0 означает недоступный план, не бесплатный тариф. Блокчейн/кошелёк/конвертация валют не подключены: поступление оператор проверяет вручную в выбранной системе.

Фиксированные верхние границы безопасности, схемы данных и container limits не являются произвольно отключаемыми переменными. Конфигурация режима не выдаёт контейнеру доступ к хосту. Команды обслуживания выполняются только в SSH, не через модель/MCP.

## Административные сценарии

Без расхода модели:

```text
найди пользователя username
пользователь 42
подписка username
продли username на 30 дней
продли username на 1 месяц
отключи username
включи username
измени username description=новое описание
```

Изменение и раскрытие ссылки имеют отдельный предпросмотр. Подтверждение привязано к единственному администратору, объекту, текущему состоянию и сроку 3 минуты. Повтор/изменившиеся данные отвергаются. При неопределённом PATCH автоматического повтора нет. Ссылки не уходят в MCP/модель, Telegram preview отключён.

Дата окончания повторно проверяется непосредственно перед записью: она должна оставаться в будущем. Проверка контракта не подменяет строковый JSON-запрос преобразованным объектом `Date` при передаче транспортному клиенту. Это важно для контракта 3.4.5: результат его преобразования даты нельзя повторно подавать на вход строковой схемы. Локальная проверка перед вызовом транспортного клиента выполняется до перехода заявки в uncertain; ошибка этой проверки оставляет rejected без PATCH. Настоящий сетевой/HTTP-сбой остаётся uncertain без автоматического повтора. Уже сохранённые старые заявки обновление не переисполняет и не переоценивает автоматически.

Дополнительный MCP запускается только в доверенном административном stdio-контексте: `start-admin-mcp.mjs --stdio --confirm-admin-context`, с теми же приватными env/file-secret/state mounts. Не публиковать stdio через незащищённый HTTP. Он не заменяет подключённые агрегатные команды чата. MCP возвращает ID заявки; в Telegram администратор открывает `заявка ID`, проверяет и нажимает подтверждение. У модели такого инструмента нет.

`prepare_user_renewal` готовит продление днями или календарными месяцами. `prepare_new_user` использует только включённый режим создания и настроенные defaults. Оба инструмента возвращают идентификатор предпросмотра. `get_user_summary` выдаёт минимальные показатели без имени, Telegram ID, описания и ссылки. Произвольных HTTP-запросов и инструмента подтверждения в этом MCP нет.

## Оплаты и продления

Клиент создаёт заявку в кабинете. Баланс до подтверждения не меняется. Администратор проверяет поступление и вводит `платеж ID система:ID-операции`; затем подтверждает предпросмотр. Сохранённый хеш операции предотвращает повторное зачисление по другой заявке. Нельзя считать скриншот доказательством оплаты.

Заявка продления фиксирует валюту, цену и дни. Кнопка администратора создаёт отдельный предпросмотр срока. Только окончательное подтверждение резервирует баланс и вызывает ограниченное изменение панели. Повтор не списывает деньги второй раз. Известный отказ до PATCH возвращает резерв; неопределённый результат удерживает его до ручной сверки. Никаких автоматических повторов/возвратов при неопределённости.

Состояния `executing`/`uncertain` требуют сверки панели и журнала: SQL-правку наугад не выполнять. Универсального автоматического разрешения таких случаев нет. Не включать реальные продажи до проверки положительного сценария, отказа, таймаута и восстановления на стенде.

## Поддержка и данные

Кабинет использует непрозрачные HttpOnly/SameSite-сессии, CSRF и проверку origin/Host. HTTPS обязателен, кроме явно локального `localhost`/`127.0.0.1` через SSH-туннель. Почта является логином: автоматическая проверка почты, SMTP, самостоятельная регистрация и восстановление пароля не заявлены реализованными. Первый доступ создаёт оператор: `./botctl business account` с двойным скрытым вводом пароля. Привязку числового пользователя следует проверить до выдачи доступа.

Истории/кеш привязаны к account ID на сервере, не к переданному клиентом ID. В общую базу не копируются чужие разговоры или ответы модели. FAQ редактируются оператором в `apps/business/faq.json`; неизменённый FAQ не стирает кеш при перезапуске. История ограничена 30 днями и 100 сообщениями; пользователю доступно удаление. Короткие контекстные ответы не становятся общими кешированными командами.

Сложное обращение попадает в очередь администратора. В боте открыть «Обращения поддержки»; ответить `ответ ID текст`. Ответ сохраняется в истории конкретного кабинета, а не отправляется всем пользователям Telegram.

Иллюстрации подключения доступны в кабинете из отдельного read-only каталога `apps/business/guides/`. Оператор добавляет свои проверенные PNG/JPEG и записи в `catalog.json`; по умолчанию изображений нет. Файлы клиентов туда не попадают, оригинальные скриншоты приложения не выдумываются. См. README каталога; каталог и изображения не заменяют инструкции для конкретной версии клиента.

ИИ поддержки использует существующий изолированный воркер, без новых OpenAI API-ключей. Его попытки и административная классификация делят один worker limit ≤100 в московские сутки и один вызов в минуту. `/budget` отдельно показывает локальный учёт бота и общий учёт воркера. Это не остаток подписки и не гарантированный точный token cap: usage-guards применяются после вызова. Ошибки считаются; защитная пауза не снимается обновлением.

Медиа принимаются только после активного обращения и разового согласия. Исходный файл декодируется в отдельном network-none/non-root контейнере и удаляется. Проверка релевантности эвристическая: ищет название разрешённого приложения в OCR, не гарантирует смысловую релевантность. Визуальное понимание без текста/полный видеоанализ не обещаются. Секреты нужно скрыть до отправки; автоматическая текстовая фильтрация не идеальна. OCR до отдельного подтверждения администратора не попадает в модель или обычную AI-историю. После проверки можно разрешить его анализ; расход подчиняется общему бюджету. Бэкапы/документы административного бота не скачиваются.

Поиск работает только для формы «найди инструкцию для happ windows» и других перечисленных в коде поддерживаемых клиентов/систем. Произвольные вопросы/персональные данные не становятся поисковым запросом. Нужен отдельный ключ Brave API: это сторонний сервис с собственными условиями оплаты, не бесплатная часть подписки. `SEARCH_DAILY_LIMIT=0..10`, default0, и `SEARCH_ALLOWED_HOSTS` ограничивают его; повтор из публичного кеша не вызывает провайдера. URL не обходятся сервером и не исполняются как команды. Источники: [Brave API](https://api-dashboard.search.brave.com/api-reference/web/search/get).

## Развёртывание и домен

`apply-all` применяет ядро и собирает/запускает только включённые модули. Базовый `apply` остаётся прежней операцией ядра. `stop-all` останавливает только собственные модули. Дополнительно доступны `voice build/start/stop/status`, `media build/start/stop/status`, `business build/start/stop/status/account/settings`.

Кабинет опубликован только на `127.0.0.1:8787`. Публичный доступ требует отдельного согласованного домена, DNS, сертификатов и reverse proxy. `apps/business/nginx.conf.template` — шаблон для nginx на хосте, не автоматически установленный proxy и не ACME-клиент. Подставлять только `PORTAL_DOMAIN` при помощи `envsubst '${PORTAL_DOMAIN}'`; проверить конфигурацию перед reload. Существующий nginx/порты/сети панели автоматически не меняются. Для nginx в другом контейнере его loopback не является loopback VPS: схему соединения согласовать отдельно, не подключать сервис к сети панели наугад.

На одном VPS с панелью проекты/volumes/networks раздельные. Нет Docker socket mounts. ASR и OCR — network none, с отдельными временными файлами и CPU/RAM limits. Изоляция не исключает конкуренцию за ресурсы: не включать все worker-модули на занятом сервере без проверки запаса. Первый публичный тест предпочтительно выполнять отдельно от панели.

Голос основан на [faster-whisper](https://github.com/SYSTRAN/faster-whisper), tiny-модель закреплена по публичной ревизии; загрузка происходит при сборке, не при запросе пользователя. OCR ограничивает форматы/пиксели/время согласно [рекомендациям Pillow](https://pillow.readthedocs.io/en/stable/handbook/security.html).

## Снимки и перенос

`./botctl backup` останавливает свои bot/ai/кабинет и создаёт приватный снимок состояния в `.ops/backups/backup.ID`. Получатели намеренно остаются остановленными. Для обычной работы после снимка — `./botctl start` и при необходимости `./botctl apply-all` для включённых дополнений. Для переноса исходный получатель не запускать одновременно с новым.

Снимок включает согласованные SQLite-копии с учётом WAL, offset, квоты и паузы. Файлы API/Telegram-токенов, Codex auth и приватные env не читаются/не копируются. Данные клиентов/хеши паролей/операционные записи в SQLite остаются чувствительными: каталог приватный, но архив не является автоматически зашифрованным. Хранить вне публичных артефактов и Git, переносить по защищённому каналу. Код восстанавливается из проверенного Git SHA, секреты/настройки вводятся оператором, ИИ авторизуется заново на новой машине.

Для восстановления выбрать ту же ревизию, собрать образы, подготовить пустые тома через Compose create **без запуска получателей**, разместить доверенный снимок под `.ops/backups`, затем `./botctl restore BACKUP_ID`. Проверяются список файлов, SHA-256 и SQLite integrity до копирования. Снимок не аутентифицирован цифровой подписью: принимать только доверенную копию. Непустое состояние не перезаписывается. Сессии кабинета и ожидающие административные подтверждения инвалидируются; расход, offset и защитные паузы сохраняются.

Нельзя восстанавливать устаревший снимок после продолжения работы исходника и считать квоту/очередь актуальными. Перенос требует остановленного источника и последнего снимка. При обрыве восстановления часть пустого назначения может быть заполнена: не запускать его до проверки, не удалять данные наугад. `rollback` готовит прежнее ядро, останавливая дополнительные модули; их данные не удаляются. Это не автоматический откат схемы биллинга/балансов. Перед будущими несовместимыми миграциями нужны отдельные migration/rollback tests.
