# Простые команды обслуживания

`botctl` работает только в root SSH-терминале Ubuntu, только с локальным Docker и Compose-проектом `panel-admin-bot`. Это не инструмент Telegram/MCP/модели: внутри контейнеров нет Docker-сокета или доступа к управлению хостом. Прочие сервисы, daemon, firewall, сети панели и ноды не меняются.

## Подключение к уже работающему проекту

После получения проверенного коммита с этим помощником, из каталога `apps/telegram-admin`:

```sh
./botctl adopt
./botctl build
./botctl check
./botctl apply
./botctl status
```

`adopt` читает из нашего работающего bot только четыре не-секретных параметра: режим ИИ, расширенного меню, суточный предел и локальный список отчётов. Не читает токены, адрес панели, списки пользователей или авторизацию. Режим сохраняется в игнорируемой Git папке `.ops/`, без перезапуска. Если настройки уже существуют, команда отказывает, а не перезаписывает их. Первый `build` нужен для появления офлайн-валидатора в новом образе.

Каждая команда проверяет сервисные метки и папку Compose-проекта. При совпадении имени с чужим checkout, неизвестном сервисе или нескольких контейнерах одного сервиса операция запрещается. Глобальные переменные выбора Docker/Compose и приватные параметры оболочки не подменяют целевой проект. Docker endpoint закреплён на локальном Unix socket. Это не универсальная поддержка rootless Docker, macOS или удалённых context.

## Ежедневные команды

| Команда | Действие |
| --- | --- |
| `./botctl status` | Состояние только наших контейнеров; не проверяет панель |
| `./botctl logs bot` | Последние 40 строк безопасного журнала бота |
| `./botctl logs ai` | Последние 40 строк сервиса ИИ, не журнала входа |
| `./botctl stop` | Останавливает только bot/ai; тома остаются |
| `./botctl start` | Проверяет настройки и запускает/пересоздаёт выбранные сервисы |
| `./botctl apply` | Явно применяет сохранённые настройки и file-secret bind mounts |
| `./botctl build` | Собирает выбранные образы без перезапуска |
| `./botctl check` | Проверяет настройки в офлайн-контейнере, без токенов и сети |

Контейнеры продолжают использовать `unless-stopped`. Помощник не меняет systemd или автозапуск Docker. После явного `stop` следует `start`; самовольное снятие операторской остановки/защитной паузы не добавлено.

`apply` использует `--no-deps --no-build --force-recreate` только для наших сервисов. Нужно дождаться healthcheck, обычно до 90 секунд. Ошибка/пауза не включает автоматический повтор модели, сброс данных или автоматический откат. После успешного healthcheck сохраняются SHA исходников и фактические ID образов для дальнейших обновлений. Healthcheck не доказывает работоспособность каждого API-отчёта: проверять выбранную кнопку отдельно. Устаревшее inline-меню после перезапуска открывается заново командой `/menu` в текущей версии интерфейса.

## Настройки без кода

```sh
./botctl settings
```

Откроется nano с четырьмя полями:

```dotenv
AI_ENABLED=true
BOT_ENHANCED_UI=true
AI_DAILY_LIMIT=100
PANEL_ALLOWED_REPORTS=all
```

- `AI_ENABLED=false`: новые вопросы не обращаются к модели; кнопки и известные вопросы остаются.
- `BOT_ENHANCED_UI=false`: прежнее меню вместо расширенного.
- `AI_DAILY_LIMIT`: целое 0..100, по умолчанию 100. Ноль блокирует новые резервирования ИИ, не стирает прошлые. Интервал одна минута, таймаут и usage-guards не меняются. Один и тот же cap передаётся bot и ai через отдельные Compose override; нельзя повышать только один ограничитель вручную.
- `PANEL_ALLOWED_REPORTS=all`, `none` или список через запятую без пробелов, например `stats,nodes,version,expiring`. Разрешены: `version,stats,nodes,expiring,users,online,node_details,hosts,profiles,internal_squads,external_squads,system,bandwidth,health`.

Это локальные разрешения нашего сервиса, не права API-токена. Запрещённый отчёт блокируется до чтения токена и вызова панели, в кнопках и локальном report-MCP. Сам токен панели, его срок и scopes не меняются. Кнопка запрещённого раздела пока остаётся видна и сообщает об ограничении. Полностью неизвестный текст может потребовать классификацию до определения запрещённого отчёта; чтобы полностью прекратить обращения модели, отключить ИИ или поставить cap 0.

Для адреса панели, имени бота, единственного администратора и старого флага чтения подписок:

```sh
./botctl config
```

Открывается только приватная `.env`, не файл токена. Допустимы четыре исходных ключа, обычные значения без shell-выражений и без секретов. Не использовать `.env` как shell-скрипт; помощник не выполняет `source` или `eval`. В nano: сохранить `Ctrl+O`, Enter; выйти `Ctrl+X`. Изменения сначала проверяются в отдельном контейнере без сети и секретов, затем атомарно заменяют файл. При ошибке исходный файл остаётся. Работающие сервисы не меняются до `./botctl apply`. Не публиковать `.env`, `.ops/` или их снимки.

## Замена токена

```sh
./botctl token panel
```

Помощник дважды спросит новый токен скрыто, проверит совпадение и формат, атомарно заменит файл с правами 0400 для UID 1000. Старое содержимое не читается, не копируется и не резервируется. Токен не передаётся аргументом команды, не печатается и не проверяется сетевым запросом. После этого `./botctl apply` пересоздаёт bind mount. Корректный формат не подтверждает актуальность токена или его API-права.

`./botctl token telegram` аналогично сохраняет уже полученное новое значение, но не перевыпускает токен в Telegram и не меняет настройки панели. Если один бот используется также для уведомлений/бэкапов, замена здесь не обновляет его значение в панели автоматически. Не заменять Telegram-токен без отдельной необходимости. Для возврата старого значения его нужно самостоятельно безопасно ввести: помощник не хранит копию.

## Обновление и откат исходников/образов

После первой успешной установки помощника:

```sh
./botctl update FULL_VERIFIED_COMMIT_SHA
./botctl apply
```

Нужен полный SHA коммита, чьи CI и изменения оператор уже проверил. Помощник не принимает `latest`, ветку или произвольную URL и не считает Git SHA подписью или доказательством доверия. Он получает данные только из существующего `origin`, отказывает при локальных изменениях и сверяет текущие исходники/образы с последним успешным `apply`. Старые исходники и два ID образов сохраняются как один предыдущий пункт. Сборка и проверка готовят обновление, но не меняют работающие контейнеры. Применение — отдельная команда.

При неудаче сборки/проверки помощник возвращает старые теги и исходники. Если interrupted обновление оставило pending, использовать `rollback` или проверенное `apply`, не удалять состояние наугад. Загруженный shell-код неизменяем в процессе обновления: checkout новой версии не дописывает команды в уже выполняемый помощник.

```sh
./botctl rollback
./botctl apply
```

Это подготовка предыдущих совместимых исходников и сохранённых локальных образов, без скачивания образов и без перезапуска до `apply`. Текущие переменные, токены, SQLite, квоты, offset, авторизация и паузы **не откатываются**. Если прежняя версия не содержит `botctl`, её образ удалён или режим ИИ несовместим, помощник отказывает. Для исходной версии до помощника остаётся ручной откат: выбрать ранее принятый SHA, пересобрать нужные образы и запустить прежними Compose-файлами без `compose.controls*.yaml`, сохранив тома. Такой старый код не применяет новые локальные ограничения отчётов/настроек cap; не использовать его как обход действующей политики.

Не запускать `down -v`, `volume rm`, `prune` или восстановление старой SQLite ради отката кода. Записанные ID образов не являются бэкапом образов; Docker cleanup может удалить их. Здесь есть только один локальный предыдущий пункт, не реестр версий и не полноценный backup/restore. Резервирование/перенос состояния — следующий отдельный этап.

## Другой VPS

Клонировать проверенный коммит в отдельную папку, выполнить прежний `configure.sh` со скрытым вводом и затем `./botctl init --enhanced` либо `./botctl init --ai --enhanced`. Далее build/check. Для ИИ отдельно выполнить вход по инструкции `SUBSCRIPTION-AI.md`, без копирования авторизации рабочего компьютера. Перед первым start остановить прежний получатель того же Telegram-бота: два VPS не должны одновременно читать его очередь. Помощник не создаёт пользователя ОС, не устанавливает пакеты, не меняет чужие сети/контейнеры и не копирует секреты со старого VPS.

## Проверки реализации

Unit-тесты проверяют cap, allowlist, запрет доступа до credentials/clientFactory, реальный локальный MCP, буквальный разбор конфигурации и отсутствие shell-interpolation. Linux-тесты запускают helper в изолированной временной папке с искусственными Docker/Git/nano: проверяют принадлежность, apply, неудачную проверку, терминал и скрытый ввод, подготовку обновления/отката и безопасное self-update. Они не обращаются к настоящему Docker или сети. Runtime-валидатор и Compose отдельно проверяются в настоящих CI-образах офлайн. Это не заменяет отдельную серверную приёмку оператором.
